The approach

Generated from the engine, not written about it

The reason this can avoid being blog spam is structural rather than editorial. Every one of the ten planners takes a length and a width — plus a depth, thickness or height where the material needs one — and every one produces a real two- or three-way comparison scenario. That means a page answering “how much concrete for a 10×10 slab” does not need anybody to write a number down. It runs the same deterministic engine the calculator runs, at those dimensions, on the server, at build time.

This pattern already exists in the codebase. PlannerMethod renders every formula and assumption as static HTML by evaluating the real engine. heroData and compareData do the same for the homepage. A size page is the third instance of a pattern that is already load-bearing — not a new kind of thing to maintain.

URL scheme

Nest under the planner rather than flattening into the root. It keeps the parent/child relationship explicit in breadcrumbs, consolidates topical signals on the planner, and stops the root namespace filling with hundreds of question-shaped URLs.

  • /concrete-calculator — hub, unchanged
  • /concrete-calculator/10x10-slab — size intent
  • /concrete-calculator/ready-mix-vs-bagged — comparison intent
  • /mulch-calculator/bags-per-cubic-yard — conversion intent

Cost intent is deliberately deprioritised, and this is the one judgement call worth arguing about. The SERP for “concrete patio cost” is Angi, HomeGuide, HomeWyse, LawnLove, Inch Calculator and Concrete Network — established domains a new site will not displace this year. Worse, those queries want installed cost including labour, which Cubitora deliberately does not calculate. Ranking there would mean either inventing labour data or answering a question the page did not ask. Both are bad trades. Quantity intent is where the real output is the best answer on the page and the competition is small sites.

Before any of it ships

Guardrails

  • Do not generate sizes combinatorially. Four to six sizes per planner, each chosen because people search it. Every slab from 8×8 to 30×30 is the thin-content trap that gets a young domain classified as scaled content abuse.
  • Every page must carry its computed answer in server-rendered HTML, the way PlannerMethod does. A page that only links to the calculator is a doorway page.
  • Do not repeat the planner's method text. Twenty pages sharing one boilerplate block is a duplicate-content problem of your own making. Each page gets the working for its dimensions.
  • No HowTo schema. Google retired those rich results in 2023; it adds markup weight and returns nothing. BreadcrumbList and FAQPage are the two that still earn their place.
  • No invented review, rating or price schema. The existing Offer at price 0 is true. Anything beyond that would not be.
  • Sitemap and llms.txt are both derived from the route list, so new pages must be added at that source or they will silently go unlisted. Fix the missing /contact entry at the same time.
  • Add a “common sizes” module to each planner hub. Without it the new pages have exactly one inbound link each and the hub gains nothing from their existence.
  • Re-run the CLS and axe suites. Twenty new routes go through the same gate as everything else — the vitals spec already iterates the project list and will need the new routes added.

One thing this roadmap cannot give you: search volumes. There is no keyword tool wired into this project, so nothing here is ranked by measured demand. The ordering comes from SERP composition I checked directly, intent quality, whether the engine can answer honestly, and commercial value. Before building past the first five, an hour in Search Console and a real keyword tool would confirm or reshuffle the tail — and Search Console will also tell you which queries the ten planners are already picking up, which is better evidence than any of this.
